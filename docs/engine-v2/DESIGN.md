# Recommendation engine v2: rule store, engine and admin dashboard

- **Status:** Draft for discussion. Nothing in this document is built yet.
- **Branch:** `engine-v2/rules-redesign`. Nothing merges to `main` until it has been tested and accepted.
- **Decisions after this draft:** the Owner's rulings of 1 Nov 2026 are in `DECISION_LOG.md` (E-08 onwards). Where the log and this document differ, the log wins; sections below are marked where they were changed.
- **Related:**
  - `DECISION_LOG.md`: every decision, drop and deviation, with the reason and how to revert.
  - `docs/adr/0001-engine-follows-workbook-rules.md`: rulings on rule order and the workbook's gaps.
  - `INPUT_GAPS.md`: input items and values that are not yet standardised.
  - `OWNER_DISCUSSION.md`: points to settle with the Owner and the Clinical Safety lead.

## 1. What this is

A full redesign of the recommendation engine. It is not a patch of `packages/engine`.

- The **rules are data, not code**. The engine runs on a **rule set** stored in a database. Code holds only the engine's mechanics (stage order, evaluating conditions, applying effects, building the trace). Adding or fixing a rule is a data change; code changes only when something major or the approach changes (`DECISION_LOG.md` E-09).
- The rule set has **the same structure as the workbook** (Recommendation Rules Engine v3.3): the same tabs, columns, row order and wording. The person who wrote the workbook must be able to read and maintain it without meeting a new structure.
- The rule set can be **updated** through the admin dashboard. Every change creates a new **version**.
- Every recommendation records the rule set version and engine version that produced it, so it can be **traced and re-created** exactly.
- **Example tables are not used** (changed 1 Nov 2026, `DECISION_LOG.md` E-10). Tab 0, Tab 0b, Tab 9 and Tab 6d section F are neither tests nor a publish gate. The rule data decides. The earlier plan to run them for a drift register is dropped.
- **Gaps are recorded, not patched.** Where a rule can't be represented because it is unclear, contradictory or incomplete, it is **exempted** (the engine doesn't run it) and recorded in the gap register, with the context the founder and Clinical Safety lead need (`DECISION_LOG.md` E-11). The rule store design doesn't bend to fit it.

## 3. The rule store

### 3.1 Same shape as the workbook

Each workbook rule tab becomes one table in the rule store, with the same name, the same columns in the same order, and one record per row. The admin dashboard shows each tab as a grid, in the same order as the workbook.

| Workbook tab | Rule store table | Kind of rules it holds | Source reference (natural key) |
|---|---|---|---|
| README | `readme` | Notes, status, change log (not executed) | row number |
| 1. State Grid | `state_grid` | The 16 states, baseline band, default lean | Cell ID (`E1M1`…) |
| 2. Experience-Intervention | `experience_triggers` | Which pathways a feeling or sensation points to | Family name + intensity band (e.g. `Anxious / fearful · High`) |
| 3a. Sensitivity Modifiers | `sensitivity_flags` | What each flag changes in tool choice | Flag (`Sound`…) |
| 3b. Context Modifiers | `contexts` | Tools allowed and excluded per setting | Context (`Exam hall`…) |
| 4. Timeline Codes | `timelines` | Codes, windows, effect on the recommendation | Code (`T0`…`TR`) |
| 5. NUCRIPCE Drivers | `drivers` | Driver definitions | Driver (`N — Novelty`…) |
| 6. Demand Type | `demand_characteristics` | Characteristic → driver tags | Characteristic |
| 6b. Need to Intervention | `needs` | Need → route, lights where offered | Need (backend name) |
| 6c. Reflect & Meditate | `reflect_meditate` (sections A–E) | Definitions, gates RF-1…MD-6, context filter | Rule ID (`RF-1`…), or section + row |
| 6d. Free & Advanced Tools | `tools_tiers` (sections A–F) | Tool tiers, safety floor, ENT-1…ENT-9, card by light | Pathway, Rule ID (`ENT-3`), or Light |
| 7. Recommendation Matrix | `patterns` + `non_negotiables` | Patterns 1–41 and the rules across every pattern | Pattern # (`7`), or footer line |
| 8. Decision Sequence | `decision_sequence` | The order the engine runs in | Step (`0. Safety screen`…) |
| 9. Worked Example | `worked_example` | Example only (drift check) | Check-in step |
| 10. Band Safety Modifiers | `bands` + `band_rules` | Bands, lights, EX-1…SF-2, RC-1…RC-5 | Band name, or Rule ID |
| 11. Journey Inputs-Outputs | `journey_layers` | Inputs and outputs per layer; the AI boundary | Layer (`5b. Band safety modifiers`…) |
| 12. Coverage Gaps | `coverage_gaps` | The workbook's own gap list | Gap ID (`G-ST1`…) |
| 0, 0b | `examples` | Examples only (drift check) | Ref (`E1M1.2`, `RF.3`…) |
| Sheet1 | not imported | Scratch notes; logged in the import report | — |

### 3.2 The two IDs

Every record has:

- **`source_ref`**: the reference the workbook author uses, e.g. `EX-1`, `RF-2`, `ENT-3`, `Pattern 17`, `E1M1`, `T0`, `G-CX2`. Where a row has no ID of its own, the reference is the tab plus the row's first column, e.g. `Tab 3b · Exam hall`. It is shown everywhere in the dashboard and the trace. It is unique within a tab and stays the same across versions as long as the row exists.
- **`id`**: a UUIDv7 generated by the database. It never changes, even if the author renames or renumbers a row, and it is what other records point to.

Each record also stores where it came from: workbook file hash, tab name, sheet row number and the cell range.

### 3.3 What a record holds

Each record has three parts.

1. **Workbook columns, word for word.** The exact text of every cell, as the author wrote it. This is what the author reads and edits.
2. **Engine columns (added).** A structured version of the row that the engine can run (section 4). They sit to the right of the workbook columns and are shaded, like the workbook's own additions. Each has a **mapping status**:
   - `exact`: the structure says exactly what the text says (e.g. Tab 4 "Due within the next 60 minutes").
   - `interpreted`: the text needed reading. The interpretation is shown next to the text and needs the author's confirmation.
   - `unresolved`: it can't be represented yet. It is linked to a gap record, and the engine ignores it.
3. **Control fields:**
   - status: active, draft, retired;
   - `safety` flag: changing the record needs Clinical Safety approval;
   - workbook version tag (v3, v3.1, v3.2, v3.3), as the workbook shading shows;
   - who changed it, when and why.

Example, Tab 10 rule EX-1:

| Rule ID | Layer | Trigger | Effect on band | Why | Status | *Engine: condition* | *Engine: effect* | *Mapping* |
|---|---|---|---|---|---|---|---|---|
| EX-1 | Experience | Any of: distress/overwhelm, anxious, anger, shame, sadness, grief, rejection, sensory overload or social hangover at High or Very High intensity; a Body PAIN sensation at High or Very High; OR shutdown/freeze at any intensity. | -1 step | A High-intensity negative experience… | v3 - tunable | any of: family ∈ {…} with intensity ≥ `High`; pain intensity ≥ `High`; shutdown present | band −1 | exact |

The workbook's own columns stay exactly as written. Only the shaded columns are new.

### 3.4 Rules the workbook doesn't contain

The engine needs some things the workbook doesn't state, such as the order between patterns (ADR 0001 §2).
- These are stored as **additions**, in an `additions` table or as extra rows, with a source of `ADR 0001`, or a later decision record.
- They are shaded and labelled as not from the workbook.
- They are never mixed into workbook text.
- If the workbook later covers the same point, the addition is retired.

### 3.5 Versions

- A **rule set version** is a frozen copy of every table at a point in time. Its version number follows the workbook (`3.3`) plus a revision (`3.3-r1`, `3.3-r2`…).
- Each version is turned into one canonical JSON document (RFC 8785, the JSON Canonicalization Scheme) and given a **SHA-256 hash**. The hash proves exactly which rules were in force.
- Lifecycle: `draft` → `in review` → `clinical sign-off` (only if a `safety` record changed) → `published` → `retired`.
- A published version can never be edited. Rolling back means publishing an earlier version again as the new current one.
- Every record keeps its own history, so the dashboard can show how one rule changed across versions.

### 3.6 Registers kept with the rule set

| Register | Holds | Who resolves it |
|---|---|---|
| **Gaps** | A rule that can't be represented, a contradiction between rules, an undefined term, a missing number, inputs no rule covers, two rules that fire together with different outcomes, and input values that aren't standardised (`INPUT_GAPS.md`). Each entry links the records involved and an example input that shows the problem. | Founder and Clinical Safety lead |
| ~~**Drift**~~ | Dropped 1 Nov 2026 (`DECISION_LOG.md` E-10). The examples are not run. Exempted rules are tracked in the Gaps register instead. | — |
| **Decisions** | Rulings that fill a gap (e.g. ADR 0001), each linked to the gap it closes | Owner / Clinical Safety lead |

## 4. How the rules are written for the engine

The structured columns use one small, strict format so the dashboard can validate, display and edit them. It follows the workbook's own vocabulary: cell, band, light, family, intensity band, sensation, context, sensitivity flag, need, demand characteristic, timeline code, driver, pathway, tool. The author should recognise every word.

### 4.1 Facts

The engine works on named **facts**. Each stage of Tab 8 produces some, and later stages read them. Examples:

| Fact | Comes from | Example value |
|---|---|---|
| `state.cell` | Tab 1 | `E3M2` |
| `band.baseline`, `band.final` | Tab 1, Tab 10 | `Conditional`, `Constrained` |
| `light` | Tab 10 | `Amber` |
| `family.<name>.intensity`, `peak.negative` | Tab 2 | `Anxious / fearful: 7` |
| `sensation.pain.intensity`, `sensation.flags` | Tab 2 sensation-led rows | `9`, `{shutdown}` |
| `context.class`, `sensitivity.count` | Tab 3a/3b | `formal`, `2` |
| `need` | Tab 6b | `{Feel calmer}` |
| `demand.present`, `demand.timeline`, `demand.characteristics` | Tabs 4, 6 | `true`, `T1`, `{Complex}` |
| `drivers` | Tabs 5, 6 | `{Urgency, Challenge}` |
| `signals.*` | Tab 11 system inputs | `declines this session: 3` |

The list of facts is itself versioned. A rule may only use facts that exist, with the right type. Anything else is rejected when it is saved.

### 4.2 Conditions

A condition is a small expression tree: `all`, `any`, `not`, comparisons, "is one of", "contains", with numbers taken from named **thresholds** (`High` = 7, `Very High` = 9, …). Thresholds are rows in the rule set, never numbers in code, as the workbook README requires. There is no free code and nothing that can loop or call out.

### 4.3 Effects

A closed list. The dashboard offers only these:

| Effect | Used by |
|---|---|
| `band.lower(n)`, `band.cap(to)`, `band.hold` | Tab 10 EX-1, CX-1, CAP-1, E4M1, NS-1, RC-3 |
| `light.set` | Tab 10 lights and Blue |
| `stop` (safety override) | Tab 7 pattern 28, Tab 10 SF-1 |
| `require` / `forbid` (a pathway, a tool, an action, in a slot: primary, alternative, queued) | Tab 10 "Engine behaviour", Tab 1 default lean, Tab 7 non-negotiables, Tab 6c gates, Tab 6d ENT rules |
| `propose` (pathway or tool, slot, wording key) | Tab 2 triggers, Tab 6b routes, Tab 7 patterns |
| `drivers.add`, `drivers.keep_only` | Tabs 5, 6, 10, Tab 7 "NUCRIPCE tags used" |
| `tools.exclude`, `tools.prefer` | Tabs 3a, 3b, 6c D |
| `support.show` | Tab 2, Tab 7, MD-6 |
| `step_cap.set` | Tab 4 |
| `copy.use` | Tab 7 CTA and alternatives wording |

### 4.4 Requirements and proposals

Every effect is one of two types:
- A **requirement** (`require`, `forbid`, `stop`, band effects) can't be overruled by a rule in a later layer.
- A **proposal** (`propose`) is a suggestion. The card is built from the highest-ranked proposals that pass every requirement.

This is how the workbook's own wording works: Tab 10 "Red: intervention forced immediately; demand deferred" is a requirement, and Tab 7 patterns propose. It makes the Red-task-first bug impossible by design.

Ranking between proposals uses the layers in ADR 0001 §2 (stored as an addition, section 3.4), then the pattern's position within its layer.

### 4.5 Safety lexicon

The risk-language phrase list (SF-1) is a rule set table:
- grouped by category;
- with an exclusions list;
- with matching options (whole word, words in between, spelling variants).

It is versioned like every other rule and marked `safety`. Who runs it on text is an interface question (`OWNER_DISCUSSION.md` O-03).

## 5. The engine

- **Input:** standard values only, checked against the rule set's input catalogue (the values listed in `INPUT_GAPS.md` once agreed). Unknown values are rejected with a clear error, never guessed.
- **Stages:** the steps of Tab 8, in that order. Each stage applies its rules and writes facts.
- **Pure and repeatable:**
  - Same input + same rule set version + same engine version gives the same card, byte for byte.
  - No clock, no randomness and no network inside the engine. Anything time-based (e.g. "recovery window still open") arrives as an input.
- **Trace,** recorded for every run:
  - each stage;
  - every rule checked, with whether it matched and, if not, the condition that failed;
  - every effect applied;
  - every proposal and whether it was used or which requirement blocked it;
  - the facts at each stage.

  The trace is what the dashboard shows as "what influenced this".
- **Checks before publish:** the workbook's own fixed rules become automatic checks run on every version before it can be published. These include:
  - "Red ⇒ Get support now visible";
  - "the primary is always a free tool" (ENT-1);
  - "Reflect and Meditate never instead of Support" (MD-6);
  - "one primary, at most two alternatives".

  A version that breaks one is blocked, and the break is recorded as a gap.
- **Format versions:** the structure of the rule set has its own version number. New kinds of rules or effects raise it, with a script that upgrades older rule sets. The engine says which format versions it can run.
- **Technology:** TypeScript, no outside libraries, in the NestJS API.

## 6. Importing the workbook

1. **Upload** the `.xlsx` in the admin dashboard. The file and its hash are stored.
2. **Read every tab** into its table, word for word, with sheet row numbers. Table-shaped tabs (1, 3a, 3b, 4, 5, 6, 6b, 6d) fill their structured columns automatically where the meaning is exact.
3. **Prose cells** (Tabs 2, 7, 8, 10, 6c) get their structured columns from a reviewed **mapping file** kept in the repo, one entry per row. Each is marked `exact`, `interpreted` or `unresolved` with a reason. Optionally, a self-hosted model drafts a structured form for a person to confirm (`OWNER_DISCUSSION.md` O-08).
4. **Import report:**
   - every rule row, with its mapping status;
   - every gap found;
   - rows that were not imported, and why (e.g. Sheet1);
   - a coverage figure: rows mapped out of rows that state a rule.

   Nothing is dropped silently.
5. **Draft version:** the result is a draft, never published automatically. Rows that are logically broken are exempted and recorded as gaps (`DECISION_LOG.md` E-10, E-11). The examples are not run.
6. **Export:** any version can be downloaded as an `.xlsx` with the same layout as the workbook, so the author can keep working in a spreadsheet and re-import.

## 7. Recording recommendations (compliance)

- **Decision record,** for every recommendation (signed-in and Browse, E-05):
  - input values and signals;
  - rule set version and its hash;
  - engine version;
  - the full trace;
  - the card shown;
  - time.

  Personal data in the record is encrypted with the user's key, as today. **Not at this stage:** v2 records are unencrypted until before launch, and replay against hashing, Browse and deletion is an open point (`DECISION_LOG.md` E-13, `OWNER_DISCUSSION.md` O-15).
- **Replay:** any record can be re-run on its original rule set version and engine version, and must give the identical card. A scheduled job replays a sample every day and alerts on any difference.
- **Old engine versions** stay runnable. Each engine release is kept, so a record from any date can be replayed.
- **Audit log:** append-only and hash-chained, so later edits can't go unnoticed. It covers rule changes, approvals, publishing, imports and register decisions.
- **Clinical safety:** rules marked `safety` can be linked to hazard-log entries, so they can support a DCB0129 safety case (see `OWNER_DISCUSSION.md` O-06).

## 8. Admin rule dashboard

A separate staff app, with the existing staff sign-in, roles and MFA. Every action is audited.

| Area | What it does |
|---|---|
| **Rule set viewer** | The current version shown tab by tab, in the workbook's layout. Workbook columns first, engine columns shaded next to them, with mapping status and gap links. Filter by tab, rule ID, workbook version, mapping status or `safety` flag. History of any row across versions. |
| **Simulator** | One dropdown per input, filled from the input catalogue, in the order of the check-in:<ul><li>entry;</li><li>state (16 cells or Not sure answers);</li><li>up to 3 feelings with intensity;</li><li>sensations with intensity;</li><li>environment, social, time, support;</li><li>sensitivity flags;</li><li>needs;</li><li>task: timeline, characteristics, "putting this off";</li><li>system signals: plan, declines, recovery window, saved practices, previous check-in for a re-check.</li></ul>Shows the card, the band step by step, the light, the drivers, and the trace ("why"). Can run the same input against two versions side by side. Any run can be saved as a test case. |
| **All-flows explorer** | Running every combination isn't practical, so it runs:<ul><li>a set that covers every pair of input values at least once;</li><li>every threshold edge (3/4, 6/7, 8/9);</li><li>a large random sample.</li></ul>Shows outcome maps (e.g. state × feeling → light and pattern), rules that never fire, inputs with no outcome, and failed checks. Runs in the background job queue. |
| **Query** | Ask the rule set and the outcomes questions, e.g.:<ul><li>"which inputs give a task as the primary in Amber";</li><li>"what does EX-1 affect";</li><li>"which rows are `interpreted`";</li><li>"which decisions in October used version 3.3-r2".</li></ul> |
| **Editor** | Changes go into a draft version only, through forms built from the format, with live validation. Before submitting, an **impact report** re-runs the explorer sample and the examples against the change ("changes 312 of 20,000 sampled outcomes"), with the differences. Approval: Product Owner; plus Clinical Safety for `safety` rows. Then publish, or roll back. |
| **Gaps and drift** | Lists, assignment to the founder or Clinical Safety lead, and resolution. Resolving can open a draft change. |
| **Import / export** | Section 6. |

## 9. Technology

| Part | Choice | Why |
|---|---|---|
| Engine | TypeScript, no dependencies, inside the NestJS API | Matches the backend. Full control of the trace and exact replay. |
| Rule format | JSON, defined by a JSON Schema generated from zod | One definition shared by the importer, API, dashboard forms and engine |
| Rule store, versions, registers, decision records | PostgreSQL (existing) via Prisma. Workbook columns and structured columns as JSONB, metadata as tables. | Already in the stack; strong consistency for versions and approvals |
| Published version bundles | Object storage (existing MinIO), named by hash | An immutable copy for replay and audit |
| Background runs (explorer, replay, import) | pg-boss (existing) | Already in the stack |
| Workbook import and export | A spreadsheet library (SheetJS or ExcelJS; to be chosen under the dependency rules) | Reads and writes `.xlsx` with the same layout |
| Admin dashboard | Next.js (as the PWA), separate app `apps/admin` | Keeps staff tools out of the user app |
| Off-the-shelf rule engines (Drools, DMN engines) | Not used | They would replace the workbook's structure with their own. The structure must stay the author's. |
| Machine learning | Not used in deciding a card | Recommendations must be explainable and replayable. ML may later study outcomes to *suggest* rule changes, which go through the same approval. |

## 10. API (outline)

- **Paths changed (E-27):** the staff routes below are built at `/v1/rulesets/...`; the recommendation route is named in M5.
- `POST /v2/recommendations`: input values → card + trace summary + versions. Works with or without an account (E-02).
- `POST /v2/recommendations/{id}/replay`: staff only; re-runs and compares.
- `GET /v2/rulesets`, `GET /v2/rulesets/{version}`, `GET /v2/rulesets/{version}/tabs/{tab}`: staff only.
- `POST /v2/rulesets/import`, `POST /v2/rulesets/{version}/changes`, `POST /v2/rulesets/{version}/submit | approve | publish | rollback`: staff only, by role.
- `POST /v2/simulate`, `POST /v2/explore`: staff only.
- `GET /v2/registers/gaps | drift`, `PATCH` to resolve: staff only, by role.

## 11. Out of scope for this work

- Free text, voice, task splitting and mapping words to values (E-04). The other team's tool sends standard values to the engine.
- Personalisation by outcomes (Tab 11 layer 12) beyond the rule set's own re-ordering rule. Kept for later.
- Everything listed as deferred in ADR 0001.
